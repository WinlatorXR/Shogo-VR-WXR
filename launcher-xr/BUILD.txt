Building ShogoVR.exe, the minimal WinlatorXR container launcher (MSVC).

  1. Open an x86 Developer prompt, or in a script use:
       cmd /c ""<VS>\Common7\Tools\VsDevCmd.bat" -arch=x86 && ..."
     where <VS> is your Visual Studio 2022+ Build Tools installation.

  2. Compile the resources and the source:
       rc.exe /nologo /fo ShogoVR.res ShogoVR.rc
       cl.exe /nologo /O2 /MT /EHsc /W3 /DUNICODE /D_UNICODE /c ShogoVR.cpp
       link.exe /nologo /SUBSYSTEM:WINDOWS /OUT:ShogoVR.exe ShogoVR.obj ShogoVR.res

  ShogoVR.exe is a windowless EXE (not a .bat, not a shortcut).  It finds
  Client.exe next to itself, or one/two folders up (so it also works from the
  overlaid ShogoVR folder next to Client.exe), launches the game with the
  -rez list described under "Custom mods" below, waits for it to exit and
  returns its exit code.

  Deploy: copy ShogoVR.exe alongside Client.exe in the WinlatorXR container
  and start it from there.  Its icon comes from assets/shogo.ico (the icon of
  Shogo.exe).

  Deploying a release means putting the rebuilt ShogoVR.exe and the ShogoVR
  sub-folder (CShell.dll, plus AUTHORS.txt / NOTICE.txt in a packaged release)
  into exactly two places - the GOG Shogo directory and the git Release/
  directory - and nowhere else.  AutoUpdate/, Release/ReadMe.txt and every
  version.txt in the tree are human-owned (hand-picked / hand-written release
  content): a build or deploy never writes them.  The public release ZIPs
  (alphas and betas included) are put together by hand too, and built EXEs are
  never tracked in git.

  CShell.dll (the mod itself, not this launcher) is built with
  build/CShell.vcxproj.  Always build and deploy it with
  build/build-and-deploy.ps1, never a bare `MSBuild /t:Rebuild`: MSBuild's
  incremental check can silently skip recompiling when a source edit lands in or
  near the same second as the previous object files, leaving out/CShell.dll
  carrying an OLD `built <date>` stamp - so the fixes are never in the build and
  a whole round of on-device testing is wasted (this happened in the 0.8 cycle).
  The script deletes the object tree, rebuilds from scratch, refuses to deploy a
  DLL older than the newest game/ source, copies to both targets, hash-checks
  them and verifies the human-owned files are untouched.  It is a local
  developer tool and is deliberately **not tracked in git** (see .gitignore).

  Auto-update:  before launching, ShogoVR.exe reads the release channel
  (see Docs/Pre-LaunchDocs/PROJECT_PLAN.md section 7) - version.txt and notes.txt from
  https://raw.githubusercontent.com/WinlatorXR/Shogo-VR-WXR/refs/heads/main/AutoUpdate/
  - and compares the version with the version.txt sitting next to the EXE.
  The compare is by VALUE: only a strictly newer online version offers the
  update (0.8 and 0.8.0 are the same; a tag such as 0.8-beta sorts below 0.8),
  so a local prerelease build is never prompted and can never be replaced by
  an older published one.  A missing local version.txt counts as a fresh
  install and still prompts.  If the online version is newer it shows a YES/NO
  box:

    A new update is available, download now?
    Version <version>: <notes>

  YES downloads version.txt and
  https://github.com/WinlatorXR/Shogo-VR-WXR/raw/refs/heads/main/AutoUpdate/CShell.dll
  into a ShogoVRUpdate folder next to the EXE, then - only once both downloads
  are complete - copies version.txt next to the EXE and CShell.dll into the
  ShogoVR folder next to Client.exe, and empties ShogoVRUpdate (keeping the
  folder).  NO, no internet, or any download/copy failure just launches the game
  with what is already installed (a failed CShell.dll copy restores the old
  version.txt so the update is offered again next time).  What happened lands in
  ShogoVR_update.log next to the EXE.

  The install assumes the ShogoVR folder already exists next to Client.exe (it
  is part of every release package); if it is missing, the CShell.dll copy
  fails, and the update is rolled back and offered again next launch (it never
  installs half an update).

  The updater links winhttp.lib; the source carries
  #pragma comment(lib, "winhttp.lib"), so the link lines above need no change.

  Release step (by hand, for stable human-approved releases only):  put the new
  CShell.dll in AutoUpdate/, rewrite AutoUpdate/notes.txt, then bump
  AutoUpdate/version.txt AND launcher-xr/version.txt to the same new number and
  commit + push - the bump is what publishes the release, and nothing reaches
  users until it is on main.
  version.txt is the release gate - nothing bumps it automatically, and a new
  DLL with an unchanged version.txt is never offered to anybody (so an early
  prerelease build can sit on main ahead of its version bump).

  Custom mods:  the launcher no longer mounts the game's Custom folder
  automatically.  Its -rez list is now:

    -windowtitle Shogo
    -rez "SHOGO.REZ" -rez "SOUND.REZ" -rez "SHOGOP*.REZ" ...
    -rez "AlwaysLoad"                 (only when <game>\AlwaysLoad exists)
    -rez "Custom"                     (whole-folder mode)
      or -rez "Custom\<checked>.rez"  (individual mode)
    +multiplayer 0 +screenwidth N +screenheight N
    -rez "ShogoVR"                    (always last, so its CShell.dll wins)

  AlwaysLoad is a folder the player creates next to Client.exe; it is mounted
  whole, with no prompt, whenever it exists.  The Custom folder is scanned for
  .rez files directly inside it (sorted, case-insensitive).  If it also holds
  another file or subfolder (the stock Custom\custom.txt is ignored), the
  player is first asked whether to load the whole folder, pick individual .rez
  files, or continue without loading; otherwise the checkbox list of .rez files
  appears directly.  Nothing is remembered between launches; the list's X /
  "Continue without loading" loads nothing from Custom.

  A player can skip every prompt with an exact, comma-separated list of
  filenames inside Custom:

    ShogoVR.exe -mods "coop.rez,someothermod.rez"

  Only exact .rez filenames resolve (case-insensitively, no subfolders), and
  unknown entries are skipped and logged.  ShogoVR is always added by the
  launcher and never needs listing; a missing Custom folder or -mods "" simply
  loads no Custom mods.  Decisions are written to ShogoVR_update.log next to
  the EXE, like the updater.
